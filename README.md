# monitoring-hw
# 1
**Вас пригласили настроить мониторинг на проект. На онбординге вам рассказали, что проект представляет из себя платформу для вычислений с выдачей текстовых отчетов, которые сохраняются на диск. Взаимодействие с платформой осуществляется по протоколу http. Также вам отметили, что вычисления загружают ЦПУ. Какой минимальный набор метрик вы выведите в мониторинг и почему?**

Нагрузку на процессор, оперативную память свободную, алерты на занимаемое пространство диска(допустив если выше 80 занято то алерт) и отображение тоже занятости диска вдашборде в виде графика по времени для того что бы видеть темп занимаемого пространства

Также мониторить la, так как может быт не всегда загружен cpu, но при этом la может быть большой из за процессов в состоянии D

По мониторингу сервиса, можно мониторить http код и если он отличный от 200 то алертить(если там логин через апач, то там другой код его тоже учесть что ответ нормальный), также можно мониторить по этому же запросу актуальность сертификата

Вот это самый минимум, дальше уже можно следить за докером через cadvisor если это в контейнере, также за nginx или apache, настроить промтейл и локи для сбора и логирование логов и выводить логи также в дашборд

# 4
**Вы, как опытный SRE, сделали мониторинг, куда вывели отображения выполнения SLA=99% по http кодам ответов. Вычисляете этот параметр по следующей формуле: summ_2xx_requests/summ_all_requests. Данный параметр не поднимается выше 70%, но при этом в вашей системе нет кодов ответа 5xx и 4xx. Где у вас ошибка?**

Нужно посмотреть какие коды в целом отдаются, скорее всего редирект 302 считается как плохой код ответа, хотя он просто перенаправляет на https, в общем нужно посмотреть каик коды сервис отдает при разных запросах

# 5
**Опишите основные плюсы и минусы pull и push систем мониторинга.**

Pull мониторинг сам опрашивает поэтому не нужно настраивать агентов, есть централизованный контроль списка таргетов и частоты опроса минусы — не работает если таргет за натом

Push агенты шлют сами работает за натом, подходит для batch-задач и событийной модели минусы — приложение должно знать адрес мониторинга, риск флуда, нет единого контроля

# 6
**Какие из ниже перечисленных систем относятся к push модели, а какие к pull? А может есть гибридные?**

Prometheus - pull, но есть push только через pushgateway, видел что юзают для систем которые не могут по другому отдавать 
TICK - push telegraf шлёт в influxDB
Zabbix - гибрид
VictoriaMetrics - гибрид, pull + push через vmagent
Nagios - по сути pull сервер дёргает проверки, но есть NRPE/NCSA
